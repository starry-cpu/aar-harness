# 00-intake — 把研究问题变成一次可执行的运行

## 目的

在动任何东西之前，把用户脑子里那个模糊的研究意图，逼成一份能写进 `run_config.json` 的规格，
并判断这次运行到底能不能自动闭合。这一步决定了后面所有工作的上限：
规格错了，跑得越久浪费越大。

## 输入

- 用户的研究问题原文（一句话最好，一段也行）。
- 目标系统的可访问性：代码库、可执行入口、依赖、能不能本地跑。
- 用户对成本与时间的容忍度。

## 产出

- `run_config.json` 草稿（`aar.py new-run` 建立骨架）。
- **闭环等级判定**：全自动 / 半自动 / 人工，写进 `run_config.closure_tier`。
- **检索源可用性探测结果**，写进 `run_config.retrieval`。
- 与用户的问答记录，落到 `<run_dir>/logs/intake.md`（后面写报告时要复述这些前提）。

## 程序

1. **建目录骨架。**

       python scripts/aar.py new-run --dir <run_dir> --config <draft config.json> --tier standard

2. **逐个问清楚下面七个问题**（一次问一组，不要一口气全抛）。答不上来的先记 `UNKNOWN`，
   后面 01-frame 会再逼一次。

   | # | 问题 | 为什么必须问 |
   |---|---|---|
   | 1 | 你想知道的到底是什么？请给出一句话的**构念**（construct）。 | 构念错了，基准就一定错 |
   | 2 | 「哪个更好」里的候选是什么？请描述**方法空间**——什么样的改动算一个方法。 | 决定制品契约与搜索空间大小 |
   | 3 | 目标系统是什么？固定不变的部分有哪些？ | 必须把非方法因素钉死，否则分数归因不了 |
   | 4 | 一次方法执行的预算是多少（时间 / 调用次数 / token / 金额）？ | 决定 runner 超时与方法的粒度 |
   | 5 | 你能接受的单次评测成本与总时长是多少？ | 决定档位与评测基准的规模 |
   | 6 | 允许使用 LLM judge 吗？如果允许，用哪个模型、要不要人工校验一批？ | 打分器类型直接影响可信度与成本 |
   | 7 | 有许可、保密或数据出境方面的限制吗？ | 会影响基准选型与能否联网 |

3. **判定闭环等级**，这是最关键的一步。追问具体的通道：

   - 有没有一个命令，输入方法、输出一个数？
   - 这个数稳不稳？同一个方法跑两次会差多少？（不知道就记 `UNKNOWN`，02-instrument 会实测）
   - 中间需不需要人看一眼？需要几次？

   判定标准：

   | 等级 | 判据 | 后续动作 |
   |---|---|---|
   | 全自动 | 方法进 → 分数出，全程无人工，单次成本可接受 | 正常走三档 |
   | 半自动 | 需要人打分或人看结论，但每人次成本可控 | 方法数上限压到 20–40，报告里显式声明结论强度下降 |
   | 人工 | 无法程序化，或每评一次要几十分钟人工 | **停在这里**，只输出「如何改造成可自动评测」的清单，不要启动 |

   论文的能量来源就是这条通道：AAR 每个方法约 30 分钟、单卡，一晚上能试上百个。
   闭环不通，harness 就只剩一个昂贵的空转器。

4. **探测检索源可用性**，据以选降级档：

       python scripts/aar.py sources probe

   把返回的 `tier`（full / basic / offline）与逐源结果写进 `run_config.retrieval`。
   没网也能跑（离线综述 + 声明），但要先知道自己在哪一档。

5. **定档位**：light（会话内，1–3 小时，冒烟与便宜域）、standard（本地 orchestrator，8–24 小时）、
   full（数天）。写进 `run_config.tier`。

6. **把草稿交给用户过一眼**，特别确认构念与方法空间这两条。

## 退出判据

同时满足：

- `python scripts/aar.py status --run <run_dir>` 能跑通（说明 run_config 可读）；
- `run_config.closure_tier` 已写入，且不是「人工」档；
- `run_config.retrieval.tier` 已写入；
- `<run_dir>/logs/intake.md` 存在，含七个问题的答案与所有 `UNKNOWN` 标记。

## 常见失败

- **用户答不上构念。** 那就先帮他收敛：问「如果两个方案 A 和 B 摆在你面前，你会看哪个数字来决定选谁」。
  答不出数字，说明这个研究问题还没准备好，回到第 3 步判人工档。
- **把「方法空间」问成了「实现细节」。** 用户容易描述他脑子里那一个方案。要的是边界：
  允许改哪些层、哪些层锁死。边界不清会导致后来的方法不可比。
- **跳过闭环判定直接开跑。** 这是最贵的错误：跑了半天才发现分数要靠人肉看，
  而此时排行榜上已经积累了一批不可比的记录。
- **没探检索源就假设能联网。** 代理、限流、key 缺失都会在 03-survey 阶段才暴露，
  那时已经浪费了一轮 librarian。
- **档位选得过大。** 第一次运行一律建议 light 或 standard 的前两小时，先把闭环验证一遍。
  论文自己也是先用 2B 级目标模型跑通，再放大到 32B/72B。
